# 何时应该先查这个项目

当需求涉及系统代理、跨平台代理客户端、V2Ray/Xray、Shadowsocks、Clash-family、Tor、OpenWrt、旁路由、订阅或规则路由时，先查本项目的能力地图，再去当前官方上游确认实现。

# 功能：系统代理与平台接入

- 已有方案：各平台客户端通常负责配置导入、代理核心生命周期、系统代理或 VPN/TUN 接入。
- 核心思路：把“协议核心”“客户端 UI”“操作系统接入”“配置/订阅”分层。
- 涉及目录：`windows/`、`android/`、`ios/`、`macos/`、`linux/`。
- 可以借鉴：平台差异清单和故障排查维度。
- 不建议复制：旧客户端命令、下载链接、截图步骤和未注明版本的配置。
- 真正需要重新开发：产品自己的策略编排、配置管理、审计、受控权限边界和当前系统 API 适配。
- 风险：代理程序拥有高网络权限；过时客户端、供应链、证书和订阅源风险高。
- 成熟度：概念 `B`；仓库内具体操作步骤 `C/D/UNKNOWN`。

# 功能：协议核心与客户端选择

**Current verification on 2026-08-09:**

- `2dust/v2rayN`、`2dust/v2rayNG`、`XTLS/Xray-core`、`MetaCubeX/ClashMetaForAndroid`、`shadowsocks/shadowsocks-android` 和 `vernesong/OpenClash` 的 GitHub 仓库当日仍显示活跃更新。
- `shadowsocks/shadowsocks-libev` 官方描述已明确为仅修复问题，未来开发转向 `shadowsocks-rust`。
- 旧 `Dreamacro/clash` 地址当前无法解析；`MetaCubeX/mihomo` 当前 GitHub 描述与过去的 Clash Meta 核心语义不一致。涉及 Clash/Mihomo 的名称、继任关系和下载源必须重新确认，不能沿用旧认知。

**Recommendation:** 复用成熟协议核心或官方维护客户端，避免自行实现加密协议、流量转发核心和复杂规则引擎。若产品只需要管理能力，应围绕稳定上游做受控适配，而不是复制核心。

# 功能：路由器、旁路由和局域网共享

- 已有设计：主路由/OpenWrt 客户端、旁路由、桌面设备充当网关、局域网共享。
- 可以借鉴：网关位置、默认路由、DNS、设备透明接入和分流问题清单。
- 不建议复制：针对旧固件、旧插件或特定硬件的命令。
- 仍需自行实现：目标网络拓扑的回滚、健康检查、权限控制和可观察性。
- 成熟度：架构思想 `B`；具体教程 `C/UNKNOWN`。

# 功能：历史方案识别

`deprecated/` 中的 GoAgent、旧 PAC、旧 iOS 配置和相关资料仅用于理解技术演化。看到这些名称时应识别为历史线索，而不是默认候选。

# 不要重复造轮子的部分

- 成熟代理协议核心、客户端生态和配置格式。
- 操作系统已有的代理/VPN/TUN 接口。
- OpenWrt 等成熟路由平台和现有插件生态。
- 常见规则路由、订阅更新和节点健康检查概念。

# 仍然值得自己实现的部分

- 符合自身权限和威胁模型的控制面。
- 对官方上游配置的最小适配层，而非协议重写。
- 可靠的来源验证、签名/哈希检查、升级和回滚。
- 与业务策略结合的审计、可观察性和故障降级。
- 只需要 5% 能力时的轻量、可审计实现。

# 决策表

| Capability | Decision | Reason |
| --- | --- | --- |
| 代理协议核心 | Reuse | 密码学、兼容性和安全维护成本高。 |
| 客户端 UI 与系统接入 | Adapt | 优先选择当前维护的官方/可信客户端，产品侧做薄适配。 |
| 路由和分流概念 | Reference | 概念通用，具体规则和平台命令易过时。 |
| 仓库内一键包/二进制 | Replace | 来源、版本、许可证和供应链状态不足。 |
| 业务控制面与审计 | Build | 属于自身产品边界和威胁模型。 |
